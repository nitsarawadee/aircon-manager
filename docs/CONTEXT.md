## 2. กติกาที่ห้ามแหก

กติกาพวกนี้มีเหตุผลรองรับ และมีเทสต์คุมอยู่หลายข้อ **ห้ามเปลี่ยนโดยไม่ถามก่อน**

1. **ไม่พึ่ง npm เลยสักตัว** — ใช้เฉพาะของที่มากับ Node (`node:sqlite`, `node:test`)
   ต้องรันได้ในอีก 3 ปีโดยไม่มีอะไรเน่า
2. **`src/` ห้ามรู้จักแพลตฟอร์ม** — ห้าม `import` `node:fs`, `node:child_process`,
   ห้ามใช้ `Buffer` สิ่งที่ต้องแตะระบบไฟล์หรือสั่งโปรแกรมอื่น ต้องอยู่ใน `platform/`
   แล้วส่งเข้ามาทาง `ctx` (ดูข้อ 4)
3. **หนึ่งงานหนึ่งคอมมิต ระบบต้องใช้งานได้ทุกคอมมิต** ห้ามข้ามขั้น
4. **ทำงานได้โดยไม่ต้องออกเน็ต** — ฟอนต์ ไอคอน โลโก้ เก็บในเครื่องหมด
   ตอนนี้ **ไม่เหลือจุดไหนที่ออกเน็ตแล้ว** บล็อกขาออกทั้งหมดได้โดยไม่กระทบอะไร
5. **ฐานข้อมูลห้ามขึ้น git เด็ดขาด** — เป็นข้อมูลจริงของบริษัท และยังมีรหัสผ่าน
   เป็นข้อความธรรมดาอยู่ข้างใน (`data/` อยู่ใน .gitignore แล้ว)
6. **แก้ฐานข้อมูลได้แค่ "เพิ่มตาราง" กับ "เพิ่มคอลัมน์"** — `src/db/migrate.js`
   เติมให้เองตอนเปิดเซิร์ฟเวอร์ ห้ามลบ ห้ามเปลี่ยนชื่อ ห้ามเปลี่ยนชนิด
   ⚠️ ตารางต้องมาก่อนคอลัมน์เสมอ เพราะตัวเติมคอลัมน์ข้ามตารางที่ยังไม่มีไปเลย
7. **คอมเมนต์และข้อความทั้งหมดเป็นภาษาไทย** อธิบาย "ทำไม" ไม่ใช่ "ทำอะไร"

## 4. แนวคิดที่ต้องเข้าใจก่อนแก้อะไร

### `_row` คือ "ลำดับที่เท่าไหร่ในผลลัพธ์" ไม่ใช่ id ถาวร

นี่คือกับดักอันดับหนึ่งของโปรเจกต์นี้ ถ้ามีคนลบแถวที่อยู่ก่อนหน้า ลำดับจะเลื่อนขึ้น
คำสั่งแก้/ลบที่ส่งตามมาจะไปโดนรายการถัดไปโดยไม่มีอะไรฟ้อง

ป้องกันด้วย `ctx.assertRowIs(...)` — ส่งค่าที่คาดไว้ไปเทียบก่อนเขียน
**ยังไม่ได้ใส่ 4 จุด** ดูข้อ 8

ผลพวงอีกอย่าง: **ห้ามเรียงลำดับข้อมูลที่ฝั่งเซิร์ฟเวอร์** (`ORDER BY row_id` เท่านั้น)
การเรียงเพื่อแสดงผลทำที่หน้าเว็บ เพราะ `_row` ติดไปกับข้อมูลแต่ละตัวอยู่แล้ว
มีเทสต์เฝ้าจุดนี้ไว้

### `platform/` ส่งเครื่องมือเข้าไปให้ `src/` ทาง Ctx

```js
new Ctx(env, state, db, { photos, pdf, docs, attachments, backup, forms })
```
`db` = ฐานข้อมูลที่เปิดแล้ว · `photos` = ตัวเก็บรูป · `pdf` = ตัวแปลง PDF
`docs` = ที่เก็บไฟล์ PDF · `attachments` = ไฟล์ที่ช่างถ่ายส่งมา
`backup` = สำรองฐานข้อมูล · `forms` = ไฟล์แบบฟอร์มแม่แบบ (.xlsx)

ไม่ส่งมาก็ต้องยังทำงานได้ แค่ฟีเจอร์นั้นใช้ไม่ได้ (เช่นบน Cloudflare ที่ไม่มีดิสก์)

### เลขที่เอกสารใช้ชุดเดียวกันทั้งระบบ

`PM` = งานล้างตามแผน · `CM` = งานซ่อมและอื่นๆ · รูปแบบ `<PM|CM><ปี2หลัก><เดือน2หลัก>-<ลำดับ>`
ทั้งใบประวัติและเอกสารดึงเลขจากชุดเดียวกัน (`usedDocNumbers` ใน history.js)
ถ้านับแยกกันจะมีสองอย่างได้เลขเดียวกันคนละเรื่อง

⚠️ เอกสารใบเดียวถือเลขได้สองเลข (`DocNo` + `DocNo2`) ตัวนับต้องเห็นทั้งสองช่อง
และตอนออกเลขสองใบรวดเดียว ต้องส่งเลขที่เพิ่งออกกลับเข้าไปเอง (`assignDocNumbers`)
เพราะตัวออกเลขนับจากแถวที่เขียนลงไปแล้วเท่านั้น — ไม่ทำสองอย่างนี้ เลขจะซ้ำ

### เคสงานซ่อม ร้อยด้วยเลขเดียวตั้งแต่เปิดจนปิด

ไม่มีตาราง "เคส" แยก — เคสคือกลุ่มใบประวัติที่ใช้ `CaseID` เดียวกัน (`repair-case.js`)
ขั้นของเคส: **ชำรุด → รอซ่อม → ซ่อมแล้ว/ปิด** หรือ **ชำรุด → รื้อถอน → เปลี่ยนเครื่อง → ปิด**

### รหัสเครื่องคือชื่อ "ตำแหน่ง" ไม่ใช่ชื่อตัวเครื่อง

`AYA-BPC-AIR-1` = แอร์ตัวที่ 1 ของไซต์บ้านภาชี เปลี่ยนตัวเครื่องกี่รอบก็ยังรหัสเดิม
การ "เปลี่ยนเครื่อง" จึงแก้ข้อมูลในแถวเดิม ไม่สร้างแถวใหม่ และเก็บสเปกเครื่องเก่าไว้ในประวัติ

### ปิดงานซ่อมต้องออกเอกสารเท่านั้น

หน้างานซ่อมเหลือปุ่มเดียวคือ **"ปิดงาน + ออกเอกสาร"** ปุ่ม "ปิดงานอย่างเดียว" ถูกเอาออก
ด้วยเหตุผลเดียวกับหัวข้อถัดไป — ปิดงานได้โดยไม่มีหลักฐาน แปลว่าตัวเลขเดินไป
โดยไม่มีอะไรยืนยันย้อนหลัง

⚠️ `saveRepairForm` จึงต้องคืนสถานะเครื่องเป็น "ใช้งานปกติ" และล้าง `Note` ให้ด้วย
ไม่ใช่แค่ลงประวัติ เพราะตอนนี้เป็นทางเดียวที่ปิดงานได้ ถ้าไม่คืนสถานะ เครื่องจะค้าง
เป็น "รอซ่อม" ตลอดไป (อาการที่แจ้งไว้ถูกย้ายไปเก็บในประวัติก่อนล้าง)

`completeRepairRecord` ถูกถอดออกจากทะเบียนคำสั่งแล้ว แต่ยังเหลือโค้ดกับเทสต์ไว้

### ปิดงานในแผนต้องมีเอกสารรองรับ

เปลี่ยนสถานะรอบเป็น **"ล้างเสร็จสิ้น"** จากหน้าแผนตรงๆ ไม่ได้ ถ้ายังไม่มีเอกสาร
ของการล้างครั้งนั้น (เครื่องตัวนั้น ปีนั้น รอบนั้น) — ดู `hasCleaningDoc` ใน plan.js

เพราะช่องสถานะเดิมกดเปลี่ยนได้เลยโดยไม่ต้องมีหลักฐาน ตัวเลขความคืบหน้ากับ
งบประมาณจึงเดินไปได้ทั้งที่ไม่มีใบงานสักใบ และถูกถามย้อนหลังไม่ได้ว่าล้างจริงไหม

ทางที่ถูกคือ **กรอกฟอร์ม** หรือ **แนบเอกสาร** แล้วระบบปิดงานให้เองพร้อมลงประวัติ
และค่าใช้จ่าย — ด่านนี้อยู่หลังจุดที่ระบบปิดงานเอง จึงไม่ไปขวางทางที่ถูกต้อง

⚠️ ตรวจเฉพาะตอน "เพิ่งเปลี่ยนเป็นเสร็จ" รอบที่ปิดไปแล้วยังแก้ราคา/ชื่อช่างได้ตามปกติ
และสถานะอื่น (นัดหมายแล้ว · ยกเลิก) ไม่ถูกกระทบ

### การนำเข้าข้อมูลเครื่อง

แก้ข้อมูลเป็นชุดได้สองทาง ใช้ตรรกะตัวเดียวกัน (`src/import.js`)
คือหน้าเว็บ (ปุ่ม "ไฟล์สำหรับแก้" → แก้ใน Excel → ปุ่ม "นำเข้า") และคำสั่ง
`scripts/export.mjs` / `scripts/import.mjs`

**กติกาที่ฝังไว้ตายตัว** — ไม่ลบเครื่องที่ไม่ได้อยู่ในไฟล์ · ช่องว่างในไฟล์ =
ไม่ยุ่งกับช่องนั้น ไม่ใช่ล้างค่าเดิม · มีข้อผิดพลาดแม้จุดเดียว = ไม่เขียนอะไรเลย

**เฉพาะทางเว็บมีเพิ่มอีก 4 ด่าน** (`planAirUnitImport` / `applyAirUnitImport`
ใน airlist.js) — กันสิทธิ์รายภูมิภาค · เทียบกับข้อมูลทั้งตารางไม่ใช่เฉพาะภูมิภาค
ของคนนำเข้า · ตอนยืนยันคำนวณแผนใหม่แล้วเทียบกับตัวเลขที่คนเห็น · สำรองก่อนเขียน

### หน้ากรอกผลการล้าง — ออกแบบให้มือถือก่อน

ช่างกรอกจากมือถือที่หน้างานจริง ไม่ใช่มานั่งกรอกที่ออฟฟิศทีหลัง
หน้านี้จึงเป็น **หน้าเต็มจอ** ไม่ใช่กล่องลอย และเช็คลิสต์ 21 ข้อเป็น **การ์ดทีละข้อ**

วัดของจริงบนจอ 375×812 ตอนยังเป็นกล่องลอย: ช่องที่เลื่อนได้สูงแค่ 477px แต่เนื้อหา
สูง 2,638px · ตารางเช็คลิสต์ล้นออกนอกกล่องจนต้องเลื่อนสองแกน · จุดที่นิ้วแตะยาก 80 จุด
หลังแก้: ช่องที่เห็น 683px · ไม่ล้นแนวนอน · จุดที่แตะยาก 0

**กติกาที่ต้องรักษาไว้**
- ทุกปุ่ม/ช่องกรอกสูงอย่างน้อย **44px** (`min-h-[44px]`) — ปล่อยให้ความสูงมาจาก
  padding อย่างเดียวจะได้ 37-42px ซึ่งพลาดบ่อยบนมือถือ
- ช่องกรอกใช้ชื่อเดิมทั้งหมด (`cf_*` และ `.cf_val[data-no][data-col]`)
  ตัวส่งข้อมูลจึงไม่ต้องแก้ตามเวลาเปลี่ยนหน้าตา
- **เก็บร่างไว้ในเครื่อง** (`localStorage`) กันข้อมูลหายตอนเน็ตหลุดหรือปิดหน้าไปเอง
  เก็บเฉพาะตัวหนังสือ ไม่เก็บรูป เพราะค่าที่วัดจากมิเตอร์หายแล้วต้องกลับไปวัดใหม่
  ส่วนรูปยังอยู่ในคลังภาพของมือถือ เลือกใหม่ได้ · และรูป 18 ใบเกินพื้นที่ที่เบราว์เซอร์ให้
  ถ้าฝืนเก็บจะพังทั้งร่างรวมถึงตัวหนังสือที่สำคัญกว่า

⚠️ `closeModal()` ล้างเนื้อหาแบบหน่วง 200ms แต่เช็คก่อนล้างว่ายังเป็นตัวเดิมอยู่หรือเปล่า
ถ้าไม่เช็ค การเปิดหน้าใหม่ภายใน 200ms จะโดนตัวจับเวลาของหน้าเก่าล้างทิ้ง กลายเป็นจอว่าง
โดยไม่มีอะไรฟ้อง (เจอจริงตอนทดสอบการกู้ร่าง)

### หน้าแบบฟอร์มเอกสาร (งานล่าสุด ทำเยอะที่สุด)

- **ตารางในหน้านี้แยกแถวละเครื่อง แต่เอกสารยังเป็นใบเดียว**
  เพราะแบบฟอร์มกระดาษออกแบบให้ใบเดียวมีสองคอลัมน์ แต่คนตามงานเป็นรายเครื่อง
- **การล้างของแต่ละเครื่องมีเลขของตัวเอง** — `DocNo` = เครื่องที่ 1 · `DocNo2` = เครื่องที่ 2
  (ชื่อไม่สมมาตรด้วยเหตุผลเดียวกับ EquipmentCondition2 คือเปลี่ยนชื่อคอลัมน์เดิมไม่ได้)
  ทั้งสองแถวเปิดเอกสารได้ และได้ใบเดียวกันซึ่งมีทั้งสองเครื่องอยู่แล้ว
  ใบเก่าที่ยังไม่มี `DocNo2` แถวที่สองใช้เลขของใบไปก่อน
- ปุ่มลบขึ้นเฉพาะแถวแรก เพราะลบทีเดียวคือลบทั้งใบ ไม่ใช่เฉพาะเครื่องนั้น
- **1 เอกสาร = ไปล้าง 1 ครั้ง** ครอบคลุมได้ถึง 2 เครื่อง
- **เวลาของใบที่รวมสองเครื่อง คิดจากช่วงที่ครอบคลุมจริง** ไม่ใช่เอาของใบแรก
  แล้วทิ้งใบหลัง และไม่ใช่บวกกันตรงๆ (`mergeWorkTime` ใน cleaningform.js)
  ล้างคนละช่วง 09:00-10:30 + 14:00-15:30 → เริ่ม 09:00 จบ 15:30 รวม 3 ชม.
  ล้างพร้อมกัน 09:00-10:30 ทั้งคู่ → เริ่ม 09:00 จบ 10:30 รวม 1 ชม. 30 นาที
  ⚠️ **ห้ามเปลี่ยนเป็นบวกตรงๆ** — หน้างานล้างสองตัวพร้อมกันเป็นเรื่องปกติ
  ซึ่งจะกรอกเวลามาทับกัน แล้วการบวกจะได้เวลาทำงานเป็นสองเท่าของที่ทำจริง
  "ครั้งเดียวกัน" = ไซต์เดียวกัน + รอบเดียวกัน + **วันเดียวกัน** ครบทั้งสามอย่าง
  กรอกทีละเครื่องได้ ระบบรวมลงใบเดิมให้ · กรอกเครื่องเดิมซ้ำจะถูกปฏิเสธพร้อมบอกเลขใบ
- **ช่องของเครื่องยึดจากเลขท้ายรหัส** ไม่ใช่ลำดับที่กรอก (ไซต์ `BKK-MBI` มี AIR-2
  มาก่อน AIR-1 ในฐานข้อมูล ถ้ายึดลำดับจะลงสลับคอลัมน์)
- **ช่องของเครื่องยึดตำแหน่งเสมอ** ล้างตัวเดียวก็ยังอยู่คอลัมน์ของตัวเอง อีกคอลัมน์เว้นว่าง
  (ไม่ยุบรวมกัน เพราะคนอ่านดูจากตำแหน่งว่าเป็นแอร์ตัวไหนของ Node)
- **ผลประเมินแยกรายเครื่อง** — `EquipmentCondition` = เครื่องที่ 1 · `EquipmentCondition2` = เครื่องที่ 2
  (ชื่อไม่สมมาตรเพราะเปลี่ยนชื่อคอลัมน์เดิมไม่ได้ ดู `slotCols` ใน cleaningform.js)
  หน้าแนบเอกสารก็แยกรายเครื่องเหมือนกัน แนบไฟล์เดียวแต่ล้างสองตัวก็บอกได้ว่าตัวไหนเป็นยังไง
- **เอกสารประกอบสดทุกครั้งที่เปิด** — `src/modules/cleaning-doc.js` สร้างเป็น HTML
  แล้วเปิดดู/ปริ้นได้ทันที
- **ไฟล์ PDF ถูกเก็บให้เองบนเซิร์ฟเวอร์** ที่ `data/docs/<ปี>/<เดือน>/` ทุกครั้งที่บันทึก
  และสร้างทับใหม่ทุกครั้งที่แนบหรือลบรูป
  · เก็บไม่ได้ต้องไม่ทำให้การบันทึกล้มเหลว (มีเทสต์คุมไว้)
- **ปุ่มดาวน์โหลดอยู่บนหน้าเอกสารที่เปิดดู ไม่ใช่ในตาราง** (เจ้าของงานว่าตารางรก
  และคนกดเปิดดูก่อนอยู่แล้ว ค่อยตัดสินใจว่าจะเอาไฟล์) แถบปุ่มลอยมุมขวาบนใส่เฉพาะ
  ตอน opts.toolbar เท่านั้น **ห้ามใส่ตลอด** เพราะหน้าเดียวกันนี้ถูกส่งให้ Chrome
  แปลงเป็น PDF ด้วย ปุ่มจะติดไปในไฟล์ (มีเทสต์คุมไว้)
- **การแปลงเป็น PDF** ให้ `platform/pdf-render.js` สั่ง Chrome/Edge ในเครื่องแปลงให้
  ไม่มีเบราว์เซอร์ก็ไม่พัง แค่ปุ่มใช้ไม่ได้และไม่มีสำเนาเก็บไว้
- **รูปถ่าย 9 ช่องต่อเครื่อง** ย่อที่เครื่องผู้ใช้เหลือด้านยาว 1600px แล้วเก็บเป็นไฟล์
  ใน `data/photos/<เลขที่เอกสาร>/` · ฝังลงหน้าเอกสารตอนเปิด ไม่มี URL ให้เปิดตรงๆ
- **แนบรูปจากในฟอร์ม และแก้ทีหลังได้จากปุ่ม "แก้รูป" ในตาราง**
  ⚠️ รูปเก็บด้วยเลขที่เอกสาร ซึ่งออกตอนกดบันทึกเท่านั้น รูปจึงถูกอมไว้ในเบราว์เซอร์
  แล้วส่งตามขึ้นไปหลังบันทึกสำเร็จ — "บันทึกสำเร็จ" กับ "รูปขึ้นครบ" จึงเป็นคนละเรื่อง
  ถ้ารูปส่งไม่ขึ้น หน้าจะไม่ปิด แต่เปลี่ยนปุ่มล่างเป็น "ส่งรูปที่เหลืออีกครั้ง"
  ซึ่งส่งเฉพาะรูป ไม่บันทึกเอกสารซ้ำ (บันทึกซ้ำไม่ได้อยู่แล้ว ระบบจะปฏิเสธ)
- **รูปต้องครบทั้ง 9 ช่องทุกเครื่อง ไม่ครบบันทึกไม่ได้** (`PHOTO_SLOTS`)
  ผมเคยเสนอให้ช่อง 7-9 (รูปวัดค่า) ขาดได้ถ้ามีเหตุผลกำกับ เพราะ 3 ช่องนั้นต้องใช้
  แคลมป์มิเตอร์ มิเตอร์วัดไฟ และเกจวัดน้ำยา ถ้าวันนั้นไม่ได้เอาไปก็ถ่ายย้อนหลังไม่ได้
  **เจ้าของงานพิจารณาแล้วไม่เอา — ใบงานต้องสมบูรณ์เท่านั้น** อย่าหยิบกลับมาเอง
  ⚠️ ด่านนี้อยู่ฝั่งหน้าเว็บอย่างเดียว เพราะตอนที่เซิร์ฟเวอร์ตรวจได้ยังไม่มีรูปให้ตรวจ
  เป็นด่านกันลืม ไม่ใช่ด่านกันคนตั้งใจเลี่ยง
- **ปุ่มเลือกหลายรูปพร้อมกัน ลงให้แค่ช่อง 1-6** (`PHOTO_BULK`) เรียงตามชื่อไฟล์
  แบบรู้จักตัวเลข · ช่างถ่ายรูปไว้หน้างานก่อนแล้วมานั่งกรอกทีหลัง เลือกทีละใบ
  คือเปิดแกลเลอรี 18 รอบต่อหนึ่งใบ ซึ่งเป็นจุดที่คนเลิกแนบกลางคัน
  ช่อง 7-9 ไม่ลงให้ เพราะดูจากลำดับชื่อไฟล์ไม่ออกว่าใบไหนวัดอะไร (เจ้าของงานสั่งเอง)
  **สองข้อนี้ไม่ขัดกัน** — "ต้องมีครบ" กับ "ใส่ให้เองได้แค่ไหน" คนละเรื่อง
- **แก้รูปได้แม้ปิดงานในแผนแล้ว** เพราะรูปไม่ได้เป็นฐานของการปิดงาน
  (วันที่ ราคา ช่าง สถานะ ประวัติ ต่างหากที่เป็น) หน้าแก้รูปจึงแก้ได้เฉพาะรูป
  ⚠️ `deleteCleaningForm` ไม่ได้เปิดรอบในแผนกลับ — ลบเอกสารแล้วรอบยังขึ้น
  "ล้างเสร็จสิ้น" อยู่ ซึ่งขัดกับกฎ "ปิดงานต้องมีเอกสาร" (ยังไม่ได้แก้)
- **หน้าตาเอกสารยึดจาก `ITEL-FM-NE-004`** (ไฟล์ PDF ควบคุมของบริษัท) ทั้งถ้อยคำ
  เส้นตาราง สี และการจัดวาง — 3 หน้า: ใบงาน 1 + หน้ารูปเครื่องละ 1

## 6. สิทธิ์ผู้ใช้

ชื่อที่โชว์ในหน้าเว็บต่างจากค่าที่เก็บในคอลัมน์ `Role` — ดู `ROLE_TITLES` ใน `src/schema.js`
(เปลี่ยนแค่ชื่อ ไม่เปลี่ยนค่าที่เก็บ เพราะโค้ดตรวจสิทธิ์ใช้รหัสเดิมหลายสิบจุด)

| เก็บใน `Role` | ชื่อที่โชว์ | ตรวจสิทธิ์แบบ |
|---|---|---|
| `Admin` | Infrastructure | Admin |
| `RegionAdmin` | Regional | RegionAdmin |
| `Staff` | Staff | RegionAdmin |
| `Supervisor` | Supervisor | RegionAdmin |
| `Contractor` | Subcontract | Contractor |

- **Admin (Infrastructure)** — เห็นทุกภูมิภาค จัดการผู้ใช้ได้ และเป็นคนเดียวที่ **อนุมัติซ่อม**
  (เปลี่ยนสถานะเป็น "รอซ่อม") ได้
- **RegionAdmin (Regional / Staff / Supervisor)** — เห็นเฉพาะภูมิภาคที่ได้รับมอบหมาย สิทธิ์รายเมนูตั้งได้
  (`edit` / `view` / `none` ต่อโมดูล) · Staff กับ Supervisor เก็บค่าของตัวเองไว้เผื่อวันหน้าให้สิทธิ์ต่างกัน
  แต่ตอนนี้ `userInfo().role` เป็น `RegionAdmin` เหมือนกันทุกอย่าง (`REGIONAL_ROLES`)
- **Contractor (Subcontract / ผู้รับเหมา)** — บัญชีที่มี `ContractorID` (รหัสบริษัทในตาราง `contractors`)
  เห็นเฉพาะ **รอบในแผนล้างที่เลือกบริษัทตัวเองไว้** (`R1/R2/R3_ContractorID` ในแผน)
  สิทธิ์ตายตัว (`CONTRACTOR_PERMISSIONS`): ดูแผนล้าง · กรอกใบล้าง · กรอกใบติดตั้ง ที่เหลือปิดหมด
  ลบเอกสารไม่ได้ · ใบล้างต้องผูกกับรอบของตัวเองเสมอ (ปิดงานจากหน้าแผนเท่านั้น)
  · ราคามาจากราคารอบในแผน (ไม่ได้ตั้ง = ราคาต่อรอบในทะเบียน) · ชื่อบริษัทบนใบมาจากชื่อที่ Admin ตั้ง
  · รอบของเจ้าอื่นบนเครื่องเดียวกันถูกล้างราคา/ชื่อออกก่อนส่งไปหน้าเว็บ
  การเปลี่ยนเครื่องก่อนออกใบติดตั้งยังเป็นงานของเจ้าหน้าที่

**มอบหมายงาน** — ช่อง "ผู้รับเหมา" ในหน้าต่างรอบของแผนล้างเป็นตัวเลือกจากรายชื่อบริษัท
(ตั้งทั้ง Node ทีเดียวได้ที่หน้าต่าง "ราย Node") รายชื่อบริษัทเกิดตอน Admin สร้างบัญชีผู้รับเหมา
(เลือกบริษัทเดิม หรือพิมพ์ชื่อใหม่ — ชื่อที่ต่างแค่ตัวพิมพ์/ช่องว่างถือเป็นเจ้าเดิม)
ช่อง `R*_Technician` เดิมยังอยู่ เป็นข้อความเก่าที่เคยพิมพ์ ใช้แสดงผลเท่านั้น ห้ามใช้ผูกสิทธิ์

การกันสิทธิ์ทำที่**เซิร์ฟเวอร์เสมอ** การซ่อนปุ่มในหน้าเว็บกันได้แค่การกดพลาด

### ขั้นอนุมัติเอกสาร (ใบล้าง PM / ใบซ่อม / ใบติดตั้ง)

ช่องลงนาม 4 ช่องบนแบบฟอร์ม = 4 ขั้น (รายละเอียดที่หัวไฟล์ `src/modules/approval.js`)

| 2 | Staff | ผู้ควบคุมงาน (Interlink) |
| 3 | Supervisor **หรือ** Regional (ใครก็ได้) | ผู้ตรวจสอบ / ผู้ตรวจรับ |
| 4 | Infrastructure | Approve (Infra) |

- กดทีละขั้นตามลำดับ ตรวจที่เซิร์ฟเวอร์ (`approveDoc`): บทบาทตรงขั้น (`userInfo().roleKey`) + ภูมิภาคของเอกสาร
- ชื่อบนเอกสาร = ชื่อบัญชีของคนที่กด วันที่ = วันที่กด (ชื่อที่พิมพ์ในช่อง "ผู้ควบคุมงาน Interlink" ไม่ใช้กับใบใหม่)
- ระหว่างรอ: PDF เปิด/โหลดได้แต่เป็นฉบับร่าง ลายน้ำ "รออนุมัติ" ชื่อไฟล์ลงท้าย `-รออนุมัติ` · สำเนาบนเซิร์ฟเวอร์เก็บเฉพาะใบที่อนุมัติครบ
- แก้รูป / รวมเครื่องเข้าใบเดิม = เนื้อเอกสารเปลี่ยน → ล้างขั้น 2-4 เริ่มใหม่ที่ขั้น 2
- ใบเก่า (ก่อนมีขั้นอนุมัติ) และใบที่เขียนมือแล้วแนบรูป ไม่มีแถวในตาราง `doc_approvals` = ไม่ต้องอนุมัติ ใช้เหมือนเดิม

### คลังแอร์ (เครื่องเก่าที่ถอดออก)

แถวในทะเบียน (`air_units`) คือ **ตำแหน่ง** ไม่ใช่ตัวเครื่อง — เปลี่ยนเครื่องแล้วแถวเดิมเป็นของเครื่องใหม่
เครื่องเก่าจึงเก็บแยกในตาราง `warehouse_units` (`src/modules/warehouse.js`) ไม่ใช่ Node ปลอมในทะเบียน
(Node ปลอมจะไปโผล่ในแผนล้าง ปฏิทิน สิทธิ์ภูมิภาค และแดชบอร์ด)

- เข้าคลังเอง: `replaceAirUnit` (เครื่องเก่า) · `moveAirUnit` (เครื่องเดิมของปลายทาง) — ตำแหน่งว่างไม่มีอะไรเข้า
- สถานะในคลัง: รื้อถอน/ปลดระวาง (อยู่ในคลัง) → Write off (ขาย/ทิ้ง) ใช้สิทธิ์แก้รายการเครื่อง ในภูมิภาคตัวเอง
- "ซ่อมไม่ได้" แต่ยังไม่เปลี่ยนเครื่อง = เครื่องยังผูกกับตำแหน่ง หน้าคลังแสดงแยกเป็น "ตำแหน่งที่เลิกใช้"
- เครื่องที่เปลี่ยนไปก่อนมีคลัง ไม่ได้ถูกย้อนเก็บ (ข้อมูลเก่าอยู่ในประวัติเป็นข้อความ)

### ขอบเขตข้อมูลใช้ตัวกรองกลางตัวเดียว

⚠️ ทุกหน้าที่กรองข้อมูลตามผู้ใช้ต้องใช้ `ctx.scopeFilter()` (หรือ `unitsInScope` /
`allowedAirCodes` ที่เรียกตัวนี้อีกที) **ห้ามเขียนเงื่อนไข `info.regions` เองในหน้าใหม่**
เพราะผู้รับเหมาไม่มีภูมิภาค มีแต่รายการเครื่องที่มีงาน — หน้าที่เขียนเงื่อนไขเองจะลืมบทบาทนี้
แล้วปล่อยข้อมูลรั่ว ส่วน `assertRegionAccess` ยังปฏิเสธผู้รับเหมาเสมอ (ปลอดภัยไว้ก่อน)
จุดที่ผู้รับเหมาต้องเข้าได้ใช้ `assertInScope(row)` แทน

⚠️ สำหรับผู้รับเหมา `scopeFilter` คือขอบเขต **เครื่อง** ไม่ใช่ขอบเขต **งาน** — เครื่องเดียวกัน
อาจมีรอบของเจ้าอื่น ของที่ผูกกับรอบ (ใบล้าง) ต้องตรวจด้วย `ctx.ownsJob(ปี, รอบ, เครื่อง)`
(ดู `cleaningFormFilter` / `assertOwnJob` ใน cleaningform.js)

⚠️ **อย่าเชื่อ Region/SiteCode ที่หน้าเว็บส่งมา** — ใบล้างเคยตรวจสิทธิ์ด้วย Region ที่ส่งมาเอง
ตอนนี้หาเครื่องจากทะเบียนแล้วเขียนข้อมูล Node ทับ (`bindToRegistry` ใน cleaningform.js)
ด่านรวมใบใช้ SiteCode ถ้าเชื่อค่าที่ส่งมา ผู้รับเหมาจะเขียนลงใบของเจ้าอื่นได้

เทสต์ `test/contractor-scope.test.mjs` ใช้ผู้รับเหมาสองเจ้าบนเครื่องเดียวกันคนละรอบ

### เอกสารแยกสิทธิ์เป็น 3 แบบ

`cleaningform` (ล้าง) · `repairform` (ซ่อม) · `installform` (ติดตั้ง) — เดิมทั้งสามแบบ
ใช้ `cleaningform` ดอกเดียว ให้สิทธิ์ใบล้างก็เท่ากับได้สิทธิ์ใบซ่อมและใบติดตั้งไปด้วย

⚠️ **การสืบทอด** (`PERMISSION_INHERITS` ใน `src/schema.js`) — ผู้ใช้ที่ยังไม่เคยตั้ง
`repairform`/`installform` ได้ค่าเดียวกับ `cleaningform` ไม่อย่างนั้นทุกคนที่ตั้งสิทธิ์ไว้ก่อน
จะเสียสิทธิ์ใบซ่อมกับใบติดตั้งทันทีที่อัปเดต หน้าแก้สิทธิ์ในเว็บมีก็อปปี้กติกานี้
**ต้องแก้ทั้งสองที่พร้อมกัน** ไม่งั้นหน้าจอแสดงค่าไม่ตรงกับที่ใช้จริง แล้วกดบันทึก
ทีเดียวสิทธิ์จะเปลี่ยนเอง

⚠️ **การกรอกเอกสารไม่ผูกกับสิทธิ์เมนูรายการเครื่อง** — โมดูลเอกสารหาเครื่องผ่าน
`unitsInScope` (กรองภูมิภาคอย่างเดียว) ไม่ใช่ `getAirList` (ซึ่งคืนค่าว่างถ้าไม่มีสิทธิ์เมนู)
เดิมใช้ `getAirList` ผลคือต้องมีสิทธิ์ดูรายการเครื่องถึงจะกรอกเอกสารได้ และระบบฟ้องว่า
"ไม่พบเครื่อง" ทั้งที่เครื่องอยู่ตรงนั้น ห้ามส่ง `unitsInScope` ให้หน้าเว็บตรงๆ

### ลิงก์กรอกเอกสารซ่อม (ไม่ต้องล็อกอิน)

เจ้าหน้าที่กด "ส่งลิงก์" ที่งานซ่อมสถานะ "รอซ่อม" → ได้ลิงก์ `/#rl=<รหัส>` → ส่งให้ช่างทางไลน์
→ ช่างกรอกฟอร์มเดียวกับในระบบ กดส่ง = ปิดงานซ่อมทันที (ไม่มีขั้นอนุมัติ ตามที่เจ้าของงานกำหนด)
→ ลิงก์เดิมใช้เพิ่มรูปกับดาวน์โหลด PDF ได้ต่ออีกอย่างน้อย 72 ชั่วโมง แล้วปิดตัวเอง

⚠️ **เป็นคำสั่งเดียวที่เขียนข้อมูลได้โดยไม่ต้องล็อกอิน** (`PUBLIC_FUNCTIONS` ใน api.js)
สิ่งเดียวที่กั้นคือรหัสในลิงก์ — 32 ไบต์สุ่ม เก็บแค่แฮช SHA-256 ใช้ได้ครั้งเดียว มีวันหมดอายุ
ยกเลิกได้ สร้างใหม่ = ของเก่าใช้ไม่ได้ เครื่องมาจากลิงก์เสมอ (ไม่เชื่อรหัสเครื่องที่ส่งมา)
ลิงก์ที่ใช้ไม่ได้ไม่ส่งข้อมูลเครื่องออกไป · เทสต์ `test/repair-link.test.mjs`

การปิดงานของลิงก์กับของฟอร์มในระบบใช้ `writeRepairForm` ตัวเดียวกัน ห้ามแยกเขียน
ไม่งั้นวันหนึ่งสองทางจะปิดงานไม่เหมือนกัน (เช่นลืมคืนสถานะเครื่อง)

ตอนขึ้นคลาวด์: ลิงก์ต้องเปิดจากข้างนอกได้ (HTTPS) และคำสั่ง PDF ของลิงก์ใช้เบราว์เซอร์
แปลงไฟล์บนเซิร์ฟเวอร์ ถ้าเครื่องไม่มี Chrome ปุ่มดาวน์โหลดจะแจ้งให้ขอไฟล์จากเจ้าหน้าที่แทน

## 7. วิธีทำงานที่ใช้กันมาตลอด (สำคัญ)

1. **ตรวจกับข้อมูลจริงก่อนสรุป** — ห้ามเดา ก๊อปฐานข้อมูลด้วย `VACUUM INTO`
   แล้ววัดจริง หลายครั้งที่ "เดาว่าเป็นบั๊ก" แล้วตรวจแล้วไม่ใช่ และกลับกันก็มี
2. **พิสูจน์ว่าเทสต์จับได้จริง** — เขียนเทสต์แล้วต้องลองทำให้พัง ดูว่ามันแดง
   แล้วค่อยย้อนกลับ ไม่งั้นไม่รู้ว่าเทสต์มีฟันหรือเปล่า
3. **สคริปต์บำรุงรักษาทุกตัว** — ดูผลก่อนได้ (ไม่ใส่ `--apply` = ไม่เขียน) ·
   สำรองก่อนเขียน · เขียนในทรานแซกชันเดียว · รันซ้ำไม่พัง
4. **รายงานตามจริง** — ถ้าวัดผิดต้องบอกและแก้ ไม่กลบ
5. **ตอบสั้น ให้คำแนะนำเดียว** ไม่ใช่กางตัวเลือกให้เลือกเยอะ
6. ⚠️ **แก้ `src/` หรือ `platform/` แล้วต้องรีสตาร์ทเซิร์ฟเวอร์** แก้ `web/index.html`
   แค่รีเฟรชหน้า

   (เมื่อก่อนพึ่ง Google Sheets) ตอนนี้เรียก API อะไรก็ throw แต่ยังคอมไพล์ผ่าน
   เลือกเอาว่าจะลบทิ้งหรือเขียนกำกับให้ชัด
5. **`getCleaningDocHtml` ยังไม่ได้ตรวจแถว** — เปิดดูอย่างเดียว ไม่ได้เขียนอะไร
   และยังกันสิทธิ์ภูมิภาคอยู่ อย่างมากคือเปิดเจอใบอื่นตอนลำดับแถวเลื่อน
6. **สคริปต์ที่เขียนไว้แล้วแต่ยังไม่ได้สั่งจริง** — ดูผลก่อนได้ทั้งคู่
   `backfill-condition2.mjs` (เติมผลประเมินเครื่องที่ 2 ให้ใบเก่า 6 ใบ) ·
   `clear-legacy-drive-links.mjs` (ล้างลิงก์ Drive ที่ค้างในฐานข้อมูล)
